# Contributing

Thanks for considering contributing to `windows-mcp-server`. Bug reports,
reproductions, and pull requests are all welcome.

Please note we have a [code of conduct](CODE_OF_CONDUCT.md); please follow it in
all your interactions with the project.

## Issues

If you find a bug, please file an issue in the [GitHub issues][GitHubIssues] page
and fill out the provided template. If you are taking the time to mention a
problem, even a seemingly minor one, it is greatly appreciated and a totally
valid contribution.

For anything that looks like a **security vulnerability**, do not open a public
issue — follow [SECURITY.md](SECURITY.md) instead.

## Development

Requirements: **Windows 10/11** (amd64 or arm64) and **Go 1.25+**. The desktop
automation packages are `//go:build windows`-tagged, so the project cannot be
meaningfully built or tested on Linux or macOS.

```powershell
go build ./...
go vet ./...
go test ./... -count=1

# The (amd64 || arm64) build tag is asserted everywhere; verify the cross-build.
$env:GOARCH='arm64'; go build ./...
```

Linting uses [golangci-lint](https://golangci-lint.run/) with the repository
config:

```powershell
golangci-lint run --config=./.golangci.yml
```

Two things worth knowing before you start editing:

- The config sets `new-from-merge-base: main` together with `whole-files: true`,
  so touching a file reports **all** of that file's issues, not just your diff.
- Formatting is `gofumpt` + `goimports` + `gci` + `golines` (~120 columns), with
  `gci` import groups ordered Standard → Default → `github.com/deploymenttheory`.
  Go files are pinned to LF line endings via `.gitattributes`.

CI runs on Windows only, for the build-tag reason above.

## Pull requests

- PR titles must follow [Conventional Commits](https://www.conventionalcommits.org/)
  — this is enforced by `.github/workflows/pr-title-validation.yml` and drives
  release automation. Accepted types: `feat`, `fix`, `docs`, `style`, `refactor`,
  `test`, `chore`, `build`, `ci`, `perf`.
- Releases and `CHANGELOG.md` are generated by release-please from those commit
  messages. Don't edit the changelog by hand.
- Fill out the pull request template, including how you tested the change. For
  anything touching the desktop engine, say what you exercised manually — the
  UI Automation tests self-skip in environments that cannot host UIA.
- If you add an MCP tool, see [CLAUDE.md](CLAUDE.md) for the tool-authoring
  conventions (parameter coercion, result semantics, and the manifest tests you
  need to update).
